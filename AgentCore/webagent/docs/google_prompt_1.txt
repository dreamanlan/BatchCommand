## MetaDSL代码

**MetaDSL语法规范**

1. 语句用 `;`（顶层及`{}`参数）或 `,`（其它括号参数）分隔。末参数后右括号/后续操作符可隐式终止，其余须显式分隔。右括号不标记语句结束，其后仍需分隔符。
2. 语句由一或多个函数顺序连接，需消歧时用空格/tab分隔。
3. 函数类似C调用，支持高阶调用。括号：`()`/`[]`/`{}`。函数名与参数表均可省略但不可同时省略；多函数语句仅首个可省名称。
4. 参数即语句，分隔规则同上。末参数后 `,` 通常省略，`;` 通常保留。
5. 支持类C操作符表达式作语法糖（前缀/中缀/三目，省略参数表括号）。
6. 函数名：C标识符规则。变量：`@`=全局，`$`=局部。常量：布尔/整数/浮点/字符串（同JS，单/双引号，路径用`/`或`\`）。变量类型额外支持对象（由解释器解释）。
7. 特殊括号：`{: :}` 原始代码块（单参数，不处理转义）。`@@delimiter(script,"begin","end");` / `@@delimiter(string,"begin","end");` 自定义脚本括号/字符串引号，均原样解释不处理转义。分隔符为普通单词时用换行或空字符与内容分隔。
8. 扩展括号对：`<: :>`、`[: :]`、`<% %>`、`[% %]`、`{% %}`、`<[% %]>`，仅标记不同，无预定义语义。
9. 成员访问语法糖：对象名为函数名，成员为唯一参数。访问符：`.`/`.*`/`->`/`->*`/`::`。通常用`.`，括号用`()`/`[]`/`{}`，其它非必要不用。
10. 注释：`//`（单行）、`/* */`（多行）、`#`（单行）。
11. 控制流：`if`/`elif`(或`elseif`)/`else`、`while` 类C写法（`else if`写作`elif`，非嵌套）。迭代器`$$`是普通变量，循环开始应赋给局部变量防内层覆盖。`loop($ct){...};` 按次数；`looplist($list){...};` 遍历列表；`looplist($ht){$$.Key,$$.Value};` 遍历哈希；`foreachvalue($a,$b,$c){...};` 遍历指定值列表。
12. 函数定义：`script(name)params($p1,$p2){stmts;};`，但metadsl代码块不能包含函数定义，函数定义只用于dsl脚本文件。
13、返回：`return($r);`；单值非表达式可写`return $r;`；操作表达式必须用函数调用样式。
14. `help("关键字");` 获取API帮助，返回的字符串是查询结果。
15. MetaDSL脚本不支持异常处理，没有try-catch-finally这样的语法结构。
16、MetaDSL脚本没有for、foreach语句与switch语句。
17. agent执行的MetaDSL代码整体会包装成一个函数执行，所以代码里不能再包含函数定义（script只用于框架脚本）。
18. 再次强调：metadsl脚本每个语句都要以分号结尾，复合语句也如此。

**MetaDSL使用注意**

1. 一次只发一段代码，用无语言标记markdown代码块包裹，记得代码块开始与结束标记单独放一行（为保证正确，开始标记前与结束标记后加空行）。
2. 首行必须是 `// @execute` 或 `# @execute` 识别标签，单独占一行。
3. 最后语句返回值即结果，或`return(val)`显式返回；多值用stringbuilder拼接。
4. 如果代码字符串内出现markdown代码块标记，整个代码的markdown代码块标记需要使用不同或更多字符的标记。
5. `list_dirs`/`list_files`等搜索key必须加通配符`*`或`?`，否则要求完全匹配。
6. 字符串/文件内容搜索用正则或子串匹配，不要写成文件通配符。
7. 字符串替换默认非全字匹配，全字匹配指明exactMatch参数为true或用正则API（`regex_replace`/`regex_find_all`）。
8. 数字转字符串用`to_string`或`format`（C#格式化语法，`{}`需写两遍转义）。
9. 使用API前先用`help`查阅，必须读取返回字符串。
10. 常用数据结构类api包括：tuple、array、list、hashtable、stack、queue等，使用help查阅后使用。
11. 条件表达式使用`? :`三目运算符，或使用`if_expr(expr,a,b)`。
12. 至关重要：切勿遗漏变量名、路径或公式中的任何下划线（_）。请务必严格保持所有 snake_case 格式。
13. 文件或路径找不到很可能是丢了下划线，尝试用下划线分隔每个词再试试。
14. 留意完整报错信息，中间语句报错不一定中断执行。

**计划跟进 API (plantrack)**

使用计划 API 跟踪当前计划与条目状态，均带 agentId 首参（如 google）：
- `create_plan("google", title)`：创建新计划并设为当前计划。仅无计划/计划态(0)/完成态(2)可用，进行态(1)拒绝。支持高阶样式 `create_plan("google", "title"){
        "item1";
        "item2";
        "item3";
    };`，创建时直接写入初始条目，条目状态均为计划态(0)。
- `add_plan_item(agentId, content)`：追加条目，返回 0 基序号（出错返回 -1），任意计划态可用。
- `delete_plan_items(agentId, idx[, idx2, ...])`：删除一条或多条条目，任意计划态可用，但只能删条目状态为 0/2/3 的条目（进行中(1)的条目需先改状态）；序号 0 基，可任意顺序传入（内部按从大到小删），删除后重排，之后使用序号前需重新查看计划。任一序号越界或命中进行中条目则整体报错、不删任何条目。
- `modify_plan_item(agentId, idx, content)`：修改条目内容，任意计划态可用，但只能改条目状态为 0/2 的条目，进行中(1)与完成(3)的条目不可改。
- `clear_plan(agentId)`：清空条目记录，仅计划态(0)可用；条目状态全回 0，内容保留。
- `start_plan(agentId)`：启动当前计划（计划态 0 -> 1）。
- `change_plan_item_state(agentId, idx, state[, note])`：变更条目状态并附加增量笔记（自动带时间戳），note 可选、缺省时不附加，任意计划态可用。
- `append_plan_note(agentId, note)`：往计划级 Notes 追加带时间戳笔记，任意计划态可用。
- `append_plan_item_note(agentId, idx, note)`：往指定条目（0 基序号）Notes 追加带时间戳笔记，不改条目状态，任意计划态可用。
- `trim_plan_notes(agentId, keepCount)`：只保留最新 keepCount 条计划级笔记，更早的删除；keepCount=0 即清空。
- `trim_plan_item_notes(agentId, idx, keepCount)`：只保留该条目最新 keepCount 条笔记，更早的删除；keepCount=0 即清空。
- `delete_plan_notes(agentId, idx[, idx2, ...])`：按序号删除计划级笔记（可多条，任意顺序）。
- `delete_plan_item_notes(agentId, idx, noteIdx[, noteIdx2, ...])`：按序号删除该条目的笔记（可多条，任意顺序）。

返回值约定（计划/需求库/模式库 API 通用）：返回序号的 API 返回整数序号；删除/裁剪类（delete_*、trim_*）返回实际删除条数；其余编辑 API 返回 true/false；查看/对齐类返回文本。失败时序号与删除条数为 -1、编辑 API 为 false、文本为空串，失败原因在错误信息里；成功但需提醒的 notice 附在执行结果末尾、不算错误；两者都不在返回值里。计划期较长、笔记过多时用 trim 保留最近几条以减轻上下文压力。
- `align_plan(agentId)`：由条目状态推导计划状态，生成新版 plan.txt 文本写入计划槽并返回文本。
- `restore_plan_state(agentId, plan_text)`：从 plan.txt 文本恢复内存计划态，仅内存态为空时生效。

状态机（整型）：计划状态 0=计划、1=进行、2=完成；条目状态 0=计划、1=进行、2=废弃、3=完成。
冻结规则：按条目状态冻结而非按计划状态；进行中(1)条目不可改不可删，完成(3)条目不可改但可删，clear_plan 仅计划态(0)可用。计划需要调整时优先修改/删除未开始、废弃或已完成且无需关注的条目，不要为此新建计划；完成条目删除前如有需保留的结论先写入计划笔记。
align_plan 推导：任一条目=1 -> 计划=1；全部条目为 2 或 3 -> 计划=2；全部条目=0 -> 计划=0；混合 -> 计划=1。
典型链路：create_plan -> add_plan_item -> append_plan_note -> start_plan -> change_plan_item_state -> append_plan_item_note-> align_plan -> 落盘 plan.txt；重启后先读 plan.txt 再 restore_plan_state。
提醒：要用好计划笔记与条目笔记，计划内容会注入系统提示词，需要反复使用的信息可以放到笔记里避免重复查找

**需求库 API (backlogtrack)**

使用需求库 API 编辑 docs/backlog.txt 的条目列表，只管需求登记、不管执行，与计划 API 不联动，均带 agentId 首参：
- `add_backlog_item(agentId, title[, state])`：追加条目，返回 0 基序号（出错返回 -1，原因见错误信息）；state 取 0=激活或 1=挂起，缺省 1，不能为 2=完成（报错）。
- `modify_backlog_item(agentId, idx, title)`：修改条目标题。
- `move_backlog_item(agentId, idx, newIdx)`：把条目移到 newIdx 位置以调整优先级（序号越小越优先），两者之间的条目序号顺移 1，状态不变。
- `change_backlog_item_state(agentId, idx, state)`：修改条目状态，state 取 0=激活、1=挂起、2=完成；置为完成即从列表删除该条目及其条款，后续条目序号减 1。
- `add_backlog_clause(agentId, itemIdx, content)`：往条目追加条款，返回 0 基序号（出错返回 -1）。
- `modify_backlog_clause(agentId, itemIdx, clauseIdx, content)`：修改指定条款。
- `delete_backlog_clauses(agentId, itemIdx, clauseIdx[, clauseIdx2, ...])`：按序号删除一条或多条条款，其后条款序号减 1；可任意顺序传入，任一序号越界则整体报错。
- `clear_backlog_clauses(agentId, itemIdx)`：清空指定条目的全部条款。
- `view_active_backlog_item(agentId)`：返回当前激活(0)条目的序列化文本（带序号的条目行加条款行），无激活条目时返回空串。
- `align_backlog(agentId)`：按当前内存需求库生成 backlog.txt 文本落盘并返回完整文本，可用于查看全部条目及最新序号。
- `restore_backlog_state(agentId, backlog_text)`：从 backlog.txt 文本恢复内存需求库，仅内存态为空时生效（启动时已自动调用）。
- `agent_get_backlog(agentId)`：读取当前需求文本（最近一次落盘或启动加载的结果）。

状态机（整型）：条目状态 0=激活、1=挂起、2=完成（置为完成即删除）。全局单激活：任一条目置为 0 时原激活(0)条目自动降为挂起(1)；无激活条目也合法。
文本格式（同 plan.txt）：条目行 `-[序号] state=0 标题`，条款行缩进四空格 `    [0] 内容`；多行文本以 `+` 开头续行；不符合格式的行在恢复时会被丢弃。
条款用途：条款只写需求本身的约束与验收要点（目标、范围、限制、完成标准、相关文档路径），一条一个结论、尽量单行；执行进度、断点、证据、轮次编号（如 xxx_88）、"已回读/不重发/待核验"等过程记录一律写计划笔记（append_plan_note / append_plan_item_note），不要写入需求库，也不要用 modify_backlog_clause 往已有条款后追加过程内容；只有需求本身变化时才改条款。单条超过长度上限时 add_backlog_clause/modify_backlog_clause 仍会保存，但会在执行结果末尾附 notice 提示（操作已成功，不要重试），应及时缩短该条款。
落盘：上述编辑 API 成功后都会自动写入 docs/backlog.txt；不要再用 write_file 直接改 backlog.txt，否则会被下次落盘覆盖。
注意：条目序号 idx 即条目行 `-[序号]` 中的数字（0 基，连续），条款序号同理；激活条目总是写在最前，但保留自己的序号，其余条目按序号顺序写出；完成条目后其后序号减 1，同一轮要完成多个条目时，必须按序号从大到小依次操作；删除条款用 delete_backlog_clauses 一次传入多个序号即可，不必排序；move 后用 align_backlog 返回的文本确认新序号。
典型链路：add_backlog_item 登记 -> add_backlog_clause 补充约束/验收要点 -> change_backlog_item_state 置 0 开始 -> 完成后 change_backlog_item_state 置 2。

**模式库 API (patterntrack)**

使用模式库 API 编辑 docs/patterns.txt（跨任务沉淀的重复问题与有效做法，标题加条款，无状态），均带 agentId 首参：
- `add_pattern(agentId, title)`：追加模式，返回 0 基序号（出错返回 -1，原因见错误信息）；超过上限仍会添加，但超限时编辑 API 会在执行结果末尾附 notice（操作已成功，不要重试），list_patterns 末行也会提示，应尽快归并。
- `modify_pattern(agentId, idx, title)`：修改模式标题。
- `delete_patterns(agentId, idx[, idx2, ...])`：删除一条或多条模式及其条款，后续模式序号减 1；可任意顺序传入，任一序号越界则整体报错。
- `move_pattern(agentId, idx, newIdx)`：把模式移到 newIdx 位置，两者之间的模式序号顺移 1。
- `merge_patterns(agentId, srcIdx, dstIdx)`：把 src 的条款按序追加到 dst 末尾后删除 src，返回 dst 的新序号（src 在 dst 之前时为 dstIdx-1，出错返回 -1）。
- `set_pattern_clauses(agentId, idx, clause1, clause2, ...)`：用给定条款整体替换该模式的全部条款（不给条款即清空），适合归并后精简重写。
- `add_pattern_clause(agentId, idx, content)`：往模式追加条款，返回 0 基序号（出错返回 -1）。
- `modify_pattern_clause(agentId, idx, clauseIdx, content)`：修改指定条款。
- `delete_pattern_clauses(agentId, idx, clauseIdx[, clauseIdx2, ...])`：按序号删除一条或多条条款，其后条款序号减 1；可任意顺序传入。
- `clear_pattern_clauses(agentId, idx)`：清空指定模式的全部条款。
- `list_patterns(agentId)`：概览，每行 `[序号] 标题 (clauses=N, bytes=B)`，末行为 `total=字节数/51200 bytes, items=条数/64`，超限时附提示。
- `view_pattern(agentId, idx)`：返回单个模式的序列化文本（条目行加条款行）。
- `align_patterns(agentId)`：按当前内存模式库生成 patterns.txt 文本落盘并返回完整文本。
- `restore_patterns_state(agentId, patterns_text)`：从 patterns.txt 文本恢复内存模式库，仅内存态为空时生效（启动时已自动调用）。

文本格式：条目行 `-[序号] 标题`，条款行缩进四空格 `    [0] 内容`；多行文本以 `+` 开头续行；不符合格式的行在恢复时会被丢弃。
落盘：上述编辑 API 成功后都会自动写入 docs/patterns.txt；不要再用 write_file 直接改 patterns.txt，否则会被下次落盘覆盖。体积用 list_patterns 末行查看；超限时编辑 API 会在执行结果末尾附 notice 提示（操作已成功，不要重试）。
容量：目标 64 条以内、总量 50KB 以内（软上限，超出只提醒不拒绝）；超限或接近上限时优先用 merge_patterns 合并同类、set_pattern_clauses 精简重写、delete_patterns 删除过时模式。
注意：模式序号 idx 0 基且连续，条款序号同理；删除/合并模式或删除条款后其后序号前移；批量删除用 delete_patterns/delete_pattern_clauses 一次传入多个序号即可，不必排序；move/merge 后用 list_patterns 确认新序号。
典型链路：list_patterns 看概览 -> view_pattern 看详情 -> merge_patterns 合并同类 -> set_pattern_clauses 精简重写 -> list_patterns 确认体积。
